# Agentic Loops in Modern AI Agent Systems

**Summary.** An agentic loop is the runtime cycle at the heart of AI agents: an LLM repeatedly receives its accumulated context, decides on an action, executes that action through a tool, and feeds the tool's observation back in until it reaches a stopping condition. This review covers the canonical ReAct pattern that originated the idea (Section 1), then how three production systems — the [OpenAI Agents SDK](https://developers.openai.com/api/docs/guides/agents/running-agents), [LangGraph](https://docs.langchain.com/oss/python/langgraph/), and [Anthropic's Claude Code / Agent SDK](https://code.claude.com/docs/en/agent-sdk/agent-loop) — implement, bound, and observe that loop (Sections 2–4). It closes with the cross-cutting engineering concerns (termination, validation, context management, observability, human-in-the-loop) and the role of the Model Context Protocol as the tool surface the loop acts through. Every claim is linked to a primary source.

## 1. The core loop pattern: ReAct

The ReAct paper ([Yao et al., arXiv:2210.03629](https://arxiv.org/abs/2210.03629)) established the pattern every modern agent loop descends from: prompt an LLM to "generate both reasoning traces and task-specific actions in an interleaved manner." The paper's mechanism is to **augment the agent's action space with the space of language** (A ∪ L), so intermediate "Thoughts" become actions the model can legitimately emit rather than internal monologue ([paper, Section 2](https://arxiv.org/html/2210.03629v3)).

The feedback structure is unchanged in today's systems: the model produces interleaved `Thought`/`Action` steps while the *environment* (a Wikipedia API, a text game) returns corresponding `Obs`ervation steps, and the model's trajectory is used for the next decision. The paper motivates this interplay: reasoning traces help the model "induce, track, and update action plans as well as handle exceptions," while actions let it "interface with and gather additional information from external sources such as knowledge bases or environments." Empirically, interacting with an external tool "overcomes prevalent issues of hallucination and error propagation" seen in pure chain-of-thought reasoning, and the reasoning traces make the agent's decisions inspectable by humans.

Anthropic condenses the same idea into the shape of a production agent: "agents" are LLMs "that dynamically direct their own processes and tool usage" in a loop that runs "until the task is complete" — as opposed to "workflows," where the LLM follows a **predefined** code path ([Building effective agents](https://www.anthropic.com/research/building-effective-agents)).

## 2. The OpenAI Agents SDK loop

The OpenAI Agents SDK's ["Running agents" guide](https://developers.openai.com/api/docs/guides/agents/running-agents) documents its loop explicitly: call the model, inspect the output, and if it requests a tool call, execute it and feed the result back to the model in a reduced-format conversation, repeating until the model produces a final answer with no further tool calls. `Session`-backed conversation state persists the thread across calls, and each agent run can hold hooks and configuration that apply for the whole loop.

The loop mechanics are visible in the SDK source. `run.py` raises `MaxTurnsExceeded` and `InputGuardrailTripwireTriggered` / `OutputGuardrailTripwireTriggered` when the run stops for limits or guardrail failures ([`src/agents/run.py`](https://github.com/openai/openai-agents-python/blob/main/src/agents/run.py)), and `run_config.py` defines `DEFAULT_MAX_TURNS = 10`, with a `max_turns` field on `RunConfig` ("set to `None` to disable the limit") ([`src/agents/run_config.py`](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_config.py)).

Guardrails slot into the loop's entry and exit points: input guardrails run before the first model call of the chain as a fast validation step, output guardrails validate the final output, and tool guardrails validate arguments **before** each tool executes, allowing a "tripwire" to intervene before side-effecting operations ([Guardrails and approvals](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)). For multi-agent runs, the SDK offers two ways to extend the loop: **handoffs**, which transfer the current agent loop to another agent, and **agents as tools**, which wrap a sub-agent as a `Tool` whose result returns into the parent loop ([Orchestration](https://developers.openai.com/api/docs/guides/agents/orchestration)). The SDK ships built-in tracing that makes each loop iteration inspectable ([Integrations and observability](https://developers.openai.com/api/docs/guides/agents/integrations-observability)).

## 3. LangGraph: the loop as a graph runtime

LangGraph re-frames the loop as a [state machine / graph](https://docs.langchain.com/oss/python/langgraph/graph-api): typed `State`, `Node`s, and `Edge`s run on the Pregel-inspired runtime, where a "step" executes nodes and parallel nodes aggregate into "super-steps," with optional checkpointing for durability. The stop/continue decision is itself an edge in the graph.

This is literal in [`create_react_agent`](https://github.com/langchain-ai/langgraph/blob/main/libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py): its `AgentState` carries `messages: Annotated[Sequence[BaseMessage], add_messages]` (the accumulated conversation, appended via a reducer) and `remaining_steps` (default **25**), and the graph routes via `tools_condition` — if the model emitted tool calls, control goes to a `ToolNode` that executes them and returns results into `messages`; otherwise the graph reaches `END` ([`chat_agent_executor.py`, lines 55–75](https://github.com/langchain-ai/langgraph/blob/main/libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py#L55-L75)). `remaining_steps` is "calculated roughly as `recursion_limit` - `total_steps_taken`," and if it drops below 2 while tool calls are pending, the run stops instead of looping forever ([`chat_agent_executor.py`, lines 432–437](https://github.com/langchain-ai/langgraph/blob/main/libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py#L432-L437)).

Termination and interruption are first-class. When a graph exceeds the step budget without reaching a stop condition, LangGraph raises `GRAPH_RECURSION_LIMIT`; complex graphs can raise the per-invocation limit via `{"recursion_limit": 1000}` in the run config ([GRAPH_RECURSION_LIMIT](https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT.md)). And for human-in-the-loop, the [`interrupt()`](https://docs.langchain.com/oss/python/langgraph/interrupts) primitive pauses the graph mid-super-step; the checkpointer persists state so a later `Command` with `thread_id` resumes the same interrupted loop.

## 4. Anthropic's loop: Claude Code and the Agent SDK

Anthropic's ["How Claude Code works"](https://code.claude.com/docs/en/how-claude-code-works) describes the loop as three blended phases: **gather context → take action → verify results**, repeated until the task is complete, with the model choosing tools ("fix the failing tests": run tests, read errors, search sources, edit, re-run). Claude Code acts as the "agentic harness" providing the tools, context management, and execution environment around the model, and each tool result "feeds back into the loop, informing Claude's next decision."

The Agent SDK exposes this same loop programmatically ([Agent SDK agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)): receive the prompt → Claude evaluates and requests tool calls → the SDK executes them and feeds results back → repeat, with each full cycle being one **turn**, until Claude produces a response with no tool calls. The loop-as-streaming-protocol is explicit: the SDK yields an `AssistantMessage` per turn (Claude's output plus requested tool calls), a `UserMessage` per tool execution with the result, and a final `ResultMessage`. Read-only tools run concurrently while stateful ones (edit, write, bash) run sequentially.

Termination is configurable: `max_turns` caps the count of tool-use turns (no limit by default) and `max_budget_usd` caps spend, both returning a `ResultMessage` with subtype `error_max_turns` / `error_max_budget_usd`; a normal finish returns `success`, and the result carries `num_turns`, `total_cost_usd`, `usage`, and `session_id`. The loop's final `stop_reason` distinguishes `end_turn`, `max_tokens`, and `refusal`. The Python SDK's [`ClaudeSDKClient`](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/client.py) binds this lifecycle to reconnectable, streaming sessions. Context is managed *within* the loop: stable prefixes are prompt-cached, and when the window fills, the SDK automatically compacts history into summaries (`compact_boundary` message) — so long-running loops trade full history for bounded context.

## 5. What makes a loop production-safe

Across the primary sources, five concerns recur:

- **Termination.** Everyone bounds the loop, because an unbounded loop runs until the model "finishes on its own," which can "run long on open-ended prompts" ([Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)). OpenAI defaults to `max_turns=10` then raises `MaxTurnsExceeded` ([`run_config.py`](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_config.py)); LangGraph uses `remaining_steps`/`recursion_limit` and raises `GRAPH_RECURSION_LIMIT`; Anthropic exposes `max_turns` and `max_budget_usd`.
- **Validation inside the loop.** OpenAI runs input/output/tool guardrails at the loop's boundaries and before each tool call ([guardrails docs](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)). Anthropic lets hooks (`PreToolUse`, `PostToolUse`, etc.) short-circuit the loop — "a `PreToolUse` hook that rejects a tool call prevents it from executing, and Claude receives the rejection message instead," letting the model self-correct ([Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)).
- **Context bounding.** Context accumulates across turns, so systems cache stable prefixes and **compact** older history; Anthropic also isolates subtask context via subagents that return only a summary to the parent loop ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)).
- **Observability & durability.** OpenAI ships built-in tracing for loop iterations ([observability](https://developers.openai.com/api/docs/guides/agents/integrations-observability)); LangGraph checkpoints loops so they can resume after a crash; Anthropic returns per-run cost/usage and supports session resume/fork ([Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)).
- **Human-in-the-loop.** LangGraph's `interrupt()` pauses for approval ([interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)); OpenAI supports human review on tools/inputs/outputs ([guardrails-approvals](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)); Anthropic gates tools via permission modes and can deny individual calls ([Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)).

## 6. MCP: the tool surface of the loop

The Model Context Protocol is not itself a loop — MCP's [architecture](https://modelcontextprotocol.io/docs/learn/architecture) is host + one client per server, where servers expose tools, resources, and prompts. Anthropic's docs state it plainly: MCP is a protocol "for **context exchange**, not dictating how AI applications use LLMs or manage the provided context." The loop lives in the host (e.g., an agent SDK); MCP supplies the tools the loop invokes. This matches how both the OpenAI Agents SDK (MCP server/client wiring is a supported integration) and Claude Code ([MCP servers connect databases, browsers, and APIs](https://code.claude.com/docs/en/agent-sdk/agent-loop#tool-execution)) integrate it: the tool-observation feedback cycle stays the model's, while MCP provides a standardized way to add new actions to its action space — the same role the ReAct paper assigned to "external sources such as knowledge bases or environments."
