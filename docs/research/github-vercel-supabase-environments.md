# Preview / Development / Production environments across GitHub, Vercel, and Supabase

**Summary.** Vercel models three deployment environments — **Development** (local), **Preview** (per branch/PR), and **Production** (production branch) — each able to carry its own environment variables, with branch-scoped preview overrides and per-deployment URLs ([Vercel environments](https://vercel.com/docs/deployments/environments), [env vars](https://vercel.com/docs/environment-variables)). GitHub Actions adds a parallel but separate `environment` concept: named deployment targets (`production`, `staging`, …) that gate jobs via protection rules (required reviewers, wait timer, deployment-branch restrictions) and scope secrets ([GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)). The two interlock through GitHub's Deployments API — Vercel's Git integration publishes `Preview`/`Production` deployment objects, which is how CI waits on or reacts to a deploy ([Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github), [wait-for-deployment-action](https://github.com/vercel/wait-for-deployment-action)). Supabase brings **preview branching**: each PR can get its own isolated database instance built from the repo's migrations, with its own API credentials, and the Supabase↔Vercel integration auto-syncs those per-branch env vars into the matching Vercel preview deployment ([Supabase branching](https://supabase.com/docs/guides/deployment/branching), [Vercel integration](https://supabase.com/docs/guides/deployment/branching/integrations)). This note documents each layer from primary sources and closes with the gaps found in this repo's current setup.

## 1. Vercel environments

### 1.1 The three environments and when each is used

Vercel's docs define "three default environments— Local, Preview, and Production": **Local Development** ("developing and testing code changes on your local machine"), **Preview** ("deploying for further testing, QA, or collaboration without impacting your live site"), and **Production** ("deploying the final changes to your user-facing site with the production domain"). "Every environment can define its own unique environment variables, like database connection information or API keys." ([Vercel environments](https://vercel.com/docs/deployments/environments))

A **Preview** deployment is created automatically when you: "Push a commit to a branch that is not your production branch (commonly `main`)", "Create a pull request (PR) on GitHub, GitLab, or Bitbucket", or "Deploy using the CLI without the `--prod` flag". **Production** is created by "pushing or merging changes into your production branch (commonly `main`)" or `vercel --prod`. Caveat: "The first deployment of a new project is always a production deployment" regardless of trigger. Custom Environments (branch tracking, attached domains, imported variables) exist on Pro/Enterprise beyond the three defaults. ([Vercel environments](https://vercel.com/docs/deployments/environments))

### 1.2 Environment-variable scoping

"For each Environment Variable, you can select one or more Environments to apply the Variable to": **Production** ("applied to your next Production Deployment… push a commit to the Production Branch (usually `main`) or run `vercel --prod`"), **Preview** ("applied to your next Preview Deployment… when you push to a branch that is not the Production Branch or run `vercel`"), **Development** ("used when running your project locally with `vercel dev`… to download Development Environment Variables, run `vercel env pull`"). Development variables "are defined in the `.env.local` file". ([Vercel environment variables](https://vercel.com/docs/environment-variables))

Env-var changes do not retroactively apply: "Changes to environment variables are not applied to previous deployments, they only apply to new deployments. You must redeploy your project to update the value of any variables you change." ([Managing environment variables](https://vercel.com/docs/environment-variables/managing-environment-variables))

### 1.3 Precedence / shadowing

Preview variables can be scoped per branch: "When you add a preview environment variable, you can choose to apply to all non-production branches or you can select a specific branch", and "Any branch-specific variables will override other preview environment variables with the same name. This means you don't need to replicate all your existing preview environment variables for each branch – you only need to add the values you wish to override." ([Vercel environment variables](https://vercel.com/docs/environment-variables))

Local/CLI precedence (lowest to highest) is: "1. Vercel project env vars (from API), 2. Local `.env` files, 3. Shell environment variables" — documented in Vercel's own CLI source ([vercel/vercel commit ffb948](https://github.com/vercel/vercel/commit/ffb948317f0c959ac57afe3d7892b11dc9b60408)).

System env vars (opt-in in project settings) include `VERCEL_ENV` ("production, preview, development, or the name of a custom environment"), `VERCEL_TARGET_ENV`, `VERCEL_URL`, `VERCEL_BRANCH_URL`, `VERCEL_PROJECT_PRODUCTION_URL`, and `VERCEL_AUTOMATION_BYPASS_SECRET`. ([System environment variables](https://vercel.com/docs/environment-variables/system-environment-variables))

### 1.4 Git integration, deploy hooks, deployment protection

Vercel "allows for automatic deployments on every branch push and merges onto the production branch". Default production branch: `main` → `master` → Bitbucket production branch → the repo's default branch; customizable per environment in Project Settings → Environments → Branch Tracking. ([Vercel git docs](https://vercel.com/docs/git))

Vercel for GitHub "will deploy every push by default… pushes and pull requests made to branches" get "a unique preview URL based on the project name, branch, and team or username", surfaced "through a comment on each pull request"; merges to the production branch go live on the custom domain. ([Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github))

**Deploy Hooks** trigger deployments from a unique URL with "an HTTP `GET` or `POST` request" — useful when you want a deploy without a new commit. ([Vercel deployments](https://vercel.com/docs/deployments))

**Deployment Protection** "lets you control who can access your preview and production URLs". On Hobby, **Standard Protection** "protects your preview deployments and deployment URLs, but your production domain remains publicly accessible"; **All Deployments** (Pro/Enterprise) protects production too. ([Deployment protection](https://vercel.com/docs/deployment-protection)) **Vercel Authentication** restricts access to Vercel users on the project; non-members get a login redirect. ([Vercel Authentication](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication)) For tooling there is **Protection Bypass for Automation**, a secret exposed as the `VERCEL_AUTOMATION_BYPASS_SECRET` system env var "to bypass protection features for all deployments… For automated tasks like end-to-end (E2E) testing", plus Shareable Links and per-domain Exceptions. ([Bypass methods](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection), [Shareable links](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/sharable-links)) Warning: "When you enable Standard Protection, the production generated deployment URL becomes restricted. Update any fetch requests that use `VERCEL_URL`…" ([Deployment protection](https://vercel.com/docs/deployment-protection))

### 1.5 Creating/editing per-environment vars (dashboard + CLI)

Dashboard: Project → Settings → Environment Variables → set value → choose which environments apply → Save (requires a redeploy). ([Managing environment variables](https://vercel.com/docs/environment-variables/managing-environment-variables))

CLI:
- Inspect: `vercel env ls production|preview|development`.
- Add: `vercel env add DATABASE_URL production`, `vercel env add DATABASE_URL preview`, `vercel env add DATABASE_URL development`; branch-scoped: `vercel env add DATABASE_URL preview feature-branch` ("This variable only applies to preview deployments triggered from the `feature-branch` branch").
- Pull/run: `vercel pull --environment=production`, `vercel pull --environment=preview --git-branch=feature-branch`, `vercel env run -e preview -- npm test`.

([Vercel CLI env reference](https://vercel.com/docs/cli/env), [Manage env vars across environments](https://vercel.com/docs/environment-variables/manage-across-environments)) Note: `vercel env add` defaults to `sensitive` for production/preview/custom targets; development stays `encrypted` because the API does not allow sensitive vars in development.

### 1.6 Generated URLs and domains

Each deployment gets a commit URL `<project-name>-<unique-hash>-<scope-slug>.vercel.app` and a branch URL `<project-name>-git-<branch-name>-<scope-slug>.vercel.app` (branch URL tracks the branch's latest changes). "This URL is publicly accessible by default, but you can configure it to be private using deployment protection." Production custom domains are auto-updated by the Git integration on production deployments. ([Generated URLs](https://vercel.com/docs/deployments/generated-urls), [Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github))

## 2. GitHub environments & CI

### 2.1 GitHub Actions environments

"Environments are used to describe a general deployment target like `production`, `staging`, or `development`… You can use environments to require approval for a job to proceed, restrict which branches can trigger a workflow, gate deployments with custom deployment protection rules, or limit access to secrets." ([GitHub deployment environments](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments))

Protection rules, per GitHub docs: **Required reviewers** ("up to six users or teams… Only one of the required reviewers needs to approve"), **Wait timer**, **Disallow admins bypass**, **Custom deployment protection rules** (GitHub Apps), **Deployment branches** (restrict which branches/tags can deploy), and **Environment secrets** ("only available to workflow jobs that use the environment… can only access these secrets after any configured rules pass"). ([Deployments and environments reference](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), [Manage environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments))

Plan note: "Users with GitHub Free plans can only configure environments for public repositories… Organizations with GitHub Team and users with GitHub Pro can configure environments for private repositories." Environments are created implicitly on first reference. ([Manage environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments))

### 2.2 Secret levels and precedence

"Secrets can be stored within GitHub at three different levels: the organization, a single repository, or a repository environment." ([GitHub engineering blog, least privilege for secrets](https://github.blog/security/application-security/implementing-least-privilege-for-secrets-in-github-actions/)) Precedence is lowest-level-wins: environment-level beats repo-level beats org-level. Also: "Organization and repository secrets are read when a workflow run is queued, and environment secrets are read when a job referencing the environment starts." Limits: 1,000 org / 100 repo / 100 environment secrets. ([GitHub secrets reference](https://docs.github.com/en/actions/reference/security/secrets)) CLI: `gh secret set --env <name>`. ([Use secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets))

### 2.3 The `environment:` key and the deployments API

`jobs.<job_id>.environment: ENVIRONMENT-NAME` puts the job "subject to any rules configured for the specified environment"; an optional `url:` surfaces in the deployments page, the visualization graph, and as the "View deployment" button in the PR timeline; `deployment: false` skips creating the deployment object while keeping env secrets and rules. ([Deploy to an environment](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/deploy-to-environment), [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idenvironment), [Control deployments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments))

### 2.4 GitHub vs Vercel environments — how they interlock

The two are separate systems. Vercel's GitHub integration **publishes GitHub Deployment objects** named `Preview`/`Production` (suffixed `Preview – <project-slug>` in monorepos); this is what lets CI poll GitHub's Deployments API — Vercel's first-party `wait-for-deployment-action` exists precisely for that, "defaults match Vercel's naming". ([vercel/wait-for-deployment-action](https://github.com/vercel/wait-for-deployment-action)) In the reverse direction, Vercel can trigger GitHub Actions via `deployment_status` or `repository_dispatch` events carrying the deployment `url` and `environment`. ([Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github)) So a GitHub `production` environment gates *your CI job*, while Vercel's `Preview`/`Production` denote deployment targets Vercel manages; both can describe the same deploy.

### 2.5 Recommended workflow patterns (Vercel's documented guidance)

Vercel's KB: the "Git integration already handles preview URLs, immutable deploys, and instant rollback, so most teams need no pipeline at all. Add GitHub Actions only for tests, security scans, performance budgets, or approval gates." Concrete patterns:
- A quality job on push/PR (build + test + lint), then deploy jobs gated by event: `deploy-preview` with `if: github.event_name == 'pull_request'`, `deploy-production` with `if: github.ref == 'refs/heads/main' && github.event_name == 'push'`.
- `vercel pull --yes --environment=preview` + `vercel build` + `vercel deploy --prebuilt` for previews; `--environment=production` + `vercel build --prod` + `vercel deploy --prebuilt --prod` for production ("The `--prebuilt` flag is the fix" for duplicate builds).
- E2E against the live preview via `on: deployment_status: types: [success]`, gated on `github.event.deployment_status.environment == 'Preview'`, reading the URL from `github.event.deployment_status.target_url`, with `VERCEL_AUTOMATION_BYPASS_SECRET` when Deployment Protection is on.
- Avoid double deploys with `"git": { "deploymentEnabled": false }` in `vercel.json`.
- Gate production promotion on CI via Deployment Checks (Add Checks → GitHub → select workflows that must pass).

([Vercel KB: GitHub Actions with Vercel](https://vercel.com/kb/guide/how-can-i-use-github-actions-with-vercel), [Vercel official GHA examples](https://github.com/vercel/examples/tree/main/ci-cd/github-actions)) GitHub's security blog recommends restricting a `production` environment's deployment branches to `main` so workflow edits on other branches can't reach prod secrets. ([Least privilege for secrets](https://github.blog/security/application-security/implementing-least-privilege-for-secrets-in-github-actions/)) Note: for fork PRs "With the exception of `GITHUB_TOKEN`, secrets are not passed to the runner when a workflow is triggered from a forked repository." ([Use secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets))

### 2.6 Built-in Vercel integration vs REST API from Actions

The built-in **Vercel for GitHub** integration is the primary mechanism (auto previews, PR comments, deployment events). Alternatively, the **REST API** `POST /v13/deployments` creates deployments with `project`, `target` (Preview/Production), and `gitSource` (`type: github`); non-git deploys upload files via `POST /v2/files` first; auth via bearer token. ([Vercel REST API create deployment](https://vercel.com/docs/rest-api/deployments/create-a-new-deployment)) In CI, prefer `VERCEL_TOKEN` over `--token` "because it avoids exposing the token in command-line arguments". ([Vercel CLI global options](https://vercel.com/docs/cli/global-options)) First-party action: `vercel/wait-for-deployment-action` (waits for Vercel deploys via GitHub's Deployments API, no Vercel token needed). Third-party (Marketplace): `amondnet/vercel-action` (wraps CLI/REST, can create GitHub Deployments), `snaplet/vercel-action`. ([vercel-action](https://github.com/marketplace/actions/vercel-action), [snaplet/vercel-action](https://github.com/snaplet/vercel-action))

## 3. Supabase environments & branching

### 3.1 Preview branching mechanics

"Supabase branches create separate environments that spin off from your main project… **Each branch is a separate environment with its own Supabase instance and API credentials.**" **Preview branches** are "ephemeral… automatically deleted when a PR is merged or closed"; **Persistent branches** (staging/QA) are "long-lived". New branches are "**Data-less by default**: new branches do not start with any data or storage objects from your main project", unless a seed file is used with the GitHub integration. ([Supabase branching](https://supabase.com/docs/guides/deployment/branching))

Each branch runs a deployment workflow: Clone → Pull → Health → Configure (from `config.toml`, "only available for Branching via GitHub") → Migrate ("Applies pending database migrations") → Seed → Deploy (Edge Functions). "If you are using GitHub integration, the same deployment workflow will be run on every commit pushed to your git branch." ([Supabase branching](https://supabase.com/docs/guides/deployment/branching))

### 3.2 GitHub integration setup

Enable under Project Settings → Integrations → GitHub Integration (authorize GitHub, choose repo, set working directory). Options: **Automatic branching** (new GitHub branch → corresponding Supabase branch; optional "Supabase changes only"), and **Deploy to production** (push/merge to production branch applies migrations, deploys Edge Functions, configures Storage buckets). Recommended: "turning on a 'required check' for the Supabase integration… prevents PRs from being merged when migration checks fail." Branch DBs are "built from the migrations you commit to your repository"; the PR gets a status comment, and each later commit runs only not-yet-applied migrations. ([Supabase GitHub integration](https://supabase.com/docs/guides/deployment/branching/github-integration))

**Plan requirement**: "You can deploy directly from GitHub on any plan… Branching (preview environments for pull requests) requires the Pro Plan." ([Supabase deployment](https://supabase.com/docs/guides/deployment)) Cost: "Database Branching… $0.01344 per branch, per hour" on Pro/Team; "Branching | Not included" on Free. ([Supabase pricing](https://supabase.com/pricing))

To fetch branch credentials in CI: `supabase --experimental branches get "$GITHUB_HEAD_REF" -o env >> $GITHUB_ENV` (yields e.g. `POSTGRES_URL_NON_POOLING`) plus a wait on the `Supabase Preview` check. ([Working with branches in CI](https://supabase.com/docs/guides/deployment/branching/working-with-branches))

### 3.3 Where keys and env vars live

The platform has "organizations" and "projects"; "An organization may contain multiple projects. Each project is a dedicated Supabase instance", and billing/subscription is per organization. ([Billing FAQ](https://supabase.com/docs/guides/platform/billing-faq), [Platform overview](https://supabase.com/docs/guides/platform)) Roles (Owner / Administrator / Developer / Read-Only) apply at org and project scope. ([Access control](https://supabase.com/docs/guides/platform/access-control))

Keys live in the **project**: API URL under Integrations → Data API, keys under Settings → API Keys. Every request is "secured behind an API gateway which requires an API Key", with RLS underneath ("The API is configured to work with Postgres's Row Level Security, provisioned behind an API gateway with key-auth enabled"). ([Supabase API](https://supabase.com/docs/guides/api)) New key types are `sb_publishable_xxx` (public) and `sb_secret_xxx`; the legacy `anon`/`service_role` keys "will be deprecated by the end of 2026". ([API keys / creating routes](https://supabase.com/docs/guides/api/creating-routes))

Because each branch is its own instance, each has its own URL/keys; per-branch secrets can be managed with encrypted dotenv files (`.env.preview`, `.env.production`, `.env.keys`) committed to the repo and decrypted by the branching executor — `config.toml` `[branches]`/`[remotes]` blocks map per-branch project IDs. ([Branching configuration](https://supabase.com/docs/guides/deployment/branching/configuration))

### 3.4 How Vercel consumes preview-branch URLs

Official integration: "With the Supabase branching integration, you can sync the Git branch used by the hosting provider with the corresponding Supabase preview branch… **Supabase automatically updates your Vercel project with the correct environment variables for the corresponding preview branches.** The synchronization happens at the time of Pull Request being opened, not at the time of branch creation." Prereqs: the **Vercel GitHub integration** and a linked Supabase ↔ Vercel project (the project-linking lives in the Supabase integrations dashboard). Race mitigation: "Supabase is always automatically re-deploying the most recent deployment of the given pull request." ([Supabase Branching + Vercel integration](https://supabase.com/docs/guides/deployment/branching/integrations))

## 4. The end-to-end flow (how the trio wires together)

1. **Developer pushes a feature branch / opens a PR** → Vercel creates a preview deployment ([Vercel environments](https://vercel.com/docs/deployments/environments), [generated URLs](https://vercel.com/docs/deployments/generated-urls)); Supabase announces a preview branch per PR with migrations applied ([Supabase GitHub integration](https://supabase.com/docs/guides/deployment/branching/github-integration)).
2. **Supabase syncs env vars into the Vercel project** at PR-open time — the new branch's URL and keys into the Preview environment — and re-deploys the PR's latest deployment to fix race conditions. ([Supabase Branching + Vercel integration](https://supabase.com/docs/guides/deployment/branching/integrations))
3. **GitHub Actions runs quality checks** on `pull_request` (build + typecheck + test + lint, scanning secrets). ([GitHub events reference](https://docs.github.com/en/actions/reference/events-that-trigger-workflows))
4. **E2E against the live preview**: trigger on `deployment_status` (`types: [success]`, `environment == 'Preview'`, `target_url` → preview URL, `VERCEL_AUTOMATION_BYPASS_SECRET` if Standard Protection is on), or wait via `wait-for-deployment-action`. ([Vercel KB](https://vercel.com/kb/guide/how-can-i-use-github-actions-with-vercel), [wait-for-deployment-action](https://github.com/vercel/wait-for-deployment-action))
5. **Production deploy**: merge to the Vercel production branch → production deployment with Production-scoped env vars ([Vercel git](https://vercel.com/docs/git), [env vars](https://vercel.com/docs/environment-variables)); Supabase's "Deploy to production" applies migrations/functions/storage to the main project ([Supabase GitHub integration](https://supabase.com/docs/guides/deployment/branching/github-integration)).
6. **Routing `NEXT_PUBLIC_SUPABASE_URL` / keys**: define the main-project values scoped to Production (and Development for local), and let Supabase's integration manage Preview values per branch; without the integration, use branch-scoped overrides `vercel env add NEXT_PUBLIC_SUPABASE_URL preview <branch>`. ([Vercel CLI env](https://vercel.com/docs/cli/env), [env vars](https://vercel.com/docs/environment-variables))
7. **RLS implications**: preview and production do **not** share keys when the integration is used, each branch has its own RLS policies built from migrations, and production data is never cloned into branches ([Supabase branching](https://supabase.com/docs/guides/deployment/branching)). Even pointing a preview build at the main project's URL+anon key is contained by the main project's RLS policies — the anon key grants no bypass ([Supabase API](https://supabase.com/docs/guides/api)).

## 5. Gaps in this repo (`grocery-tracker-web`)

Findings below are based on reading `.github/workflows/web-quality.yml`, `.env.local.example`, `supabase/config.toml`, `AGENTS.md`, and `docs/`. No `vercel.json` exists.

1. **No deployment pipeline in CI.** The only workflow (`web-quality.yml`) runs `quality` (secrets scan, lint, typecheck, unit tests, build), `database` (local Supabase via `supabase/setup-cli@v1` + `up` migration + security-contract SQL), and `e2e` (local Supabase + `npm run dev` webServer + Playwright). There is no preview deploy, no production deploy, and E2E never runs against a live Vercel preview — all contradicting the documented pattern the trio enables ([Vercel KB](https://vercel.com/kb/guide/how-can-i-use-github-actions-with-vercel)). Adding deploy jobs requires a `vercel.json` with `"git": { "deploymentEnabled": false }` to avoid double deploys — none exists.
2. **No GitHub environments.** No `jobs.<job_id>.environment` anywhere; no `production` environment with required reviewers, wait timer, or a deployment-branch rule limiting deploys to `main`; production Vercel credentials are not environment-scoped. ([Manage environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments), [deploy to environment](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/deploy-to-environment))
3. **E2E only ever targets localhost.** `quality/e2e-environment.ts` requires `E2E_ALLOW_REMOTE=true` + `E2E_TARGET_ENV=test|staging` for non-local targets and forbids remote writes — so a read-only smoke test against a Vercel preview is possible but unconfigured. The documented `deployment_status`-driven approach is absent.
4. **Deployment protection unaccounted for.** AGENTS.md recommends sharing preview URLs and the repo's MCP usage references `vercel_web_fetch_vercel_url` (protected previews), but Standard Protection / Vercel Authentication and the `VERCEL_AUTOMATION_BYPASS_SECRET` workflow are not configured or documented; with Standard Protection on, `VERCEL_URL`-based fetches break. ([Deployment protection](https://vercel.com/docs/deployment-protection))
5. **Supabase Branching not set up.** `supabase/config.toml` has localhost-only `site_url` / `additional_redirect_urls` and no `[branches]` block; there is no `supabase/seed.sql`, so branches would be seed-less; Branching requires the Pro plan ([Supabase deployment](https://supabase.com/docs/guides/deployment)). Critically, shipping the current localhost `site_url` to preview branches would break Auth redirects for preview deployments; preview domains must be in `additional_redirect_urls`. ([Branching configuration](https://supabase.com/docs/guides/deployment/branching/configuration))
6. **Legacy key naming.** `.env.local.example` and AGENTS.md still use `NEXT_PUBLIC_SUPABASE_ANON_KEY`; Supabase deprecates `anon`/`service_role` by end of 2026 in favor of `sb_publishable_xxx` / `sb_secret_xxx`. ([API keys](https://supabase.com/docs/guides/api/creating-routes))
7. **AGENTS.md env guidance is correct but incomplete.** Rule 1 (add URL + key to Preview, Production, AND Development) matches the docs; it doesn't cover branch-scoped preview overrides, custom environments, or the redeploy-on-change rule ([Vercel env vars](https://vercel.com/docs/environment-variables), [CLI env](https://vercel.com/docs/cli/env)).
